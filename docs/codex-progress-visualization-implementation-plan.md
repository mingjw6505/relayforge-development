# Codex 进度可视化：只读旁路实现方案

> 状态：目标实现规格；已交付范围和未完成验收见[实施报告](codex-progress-visualization-implementation-report.md)。
>
> 目标宿主：Codex 桌面端；CLI 作为单独验证的兼容目标。
>
> 插件基线：`fb8f29f`；实施提交版本：`0.1.12`。
>
> 调研日期：2026-11-06。公开源码不代表用户安装版本已支持相同能力。

## 1. 决策摘要

采用“能力验证 → 只读本地看板 → 有条件增强 Codex 内展示”的路线。

1. 不修改插件的路由、Skill、开发步骤、验证门禁、交付选择、授权规则、Hook 注册及日志写入协议。
2. 在插件运行路径外增加独立的 **RelayForge Progress Companion**，只读用户选定的现有元数据日志。
3. 第一版展示“可观测会话活动 + Agent 已声明结果”，不冒充完整业务阶段进度。
4. Codex 自然产生的原生计划继续由 Codex 展示；不为可视化强迫 Agent 新增计划、工具调用或汇报步骤。
5. 先验证真实 Codex 版本的原生计划、合法只读订阅以及 MCP App UI 能力。未验证的适配器默认禁用。
6. 稳定交付入口是本地浏览器看板。若正式内嵌机制通过验证，再复用同一状态模型增加内嵌视图，不重写插件逻辑。
7. 所有控制开发的按钮均不在范围内：不能通过看板暂停 Agent、批准权限、重跑命令、提交或推送。

**需要提前接受的能力边界：**在完全不增加生产侧状态信号的前提下，无法凭空获得“当前正在实现哪个需求、测试通过了多少项、正在等待哪项审批”。第一版可以让运行活动、失败和历史结果直观可见，但不会承诺不存在的数据。业务阶段可视化属于有真实数据源才启用的增强能力。

## 2. 用户价值与非目标

### 2.1 用户能够回答的问题

- 当前选定会话最近是否有可观测活动？最后发生了什么？
- 哪些工具调用有开始记录、哪些已经结束、哪些返回失败？
- 最近一次可观测执行持续了多久？是否缺失配对事件？
- 已有工作流声明选择了什么路线，记录了什么验证和交付状态？
- 当前信息是否完整、新鲜、已经中断，还是仅仅没有新事件？
- 为什么界面没有阶段或测试详情：宿主不支持、未启用采集，还是数据本来就没有？

### 2.2 明确不做

- 不计算没有可靠分母的总完成百分比和预计剩余时间。
- 不把工具次数、Skill 数量或 Token 数量转换成任务完成度。
- 不从 `shell`、`exec_command` 等工具名称猜测设计、实现或测试阶段。
- 不把工具退出成功当作测试通过、验收通过或开发完成。
- 不读取原始对话、命令、代码、补丁、工具输入输出及 Codex 私有数据库。
- 不解析聊天中的自然语言进度清单，不用额外模型做状态分类。
- 不安装新 Hook、不修改既有 Hook、不强制信任采集、不自动改变 Codex 配置。
- 不提供云端同步、团队共享、远程访问、后台自动开机启动或自动升级。
- 不把“插件已安装”展示成“本次任务确认运行了插件”。

## 3. 当前系统事实与能力缺口

### 3.1 已核实的仓库基础

| 项目 | 当前行为 | 对方案的影响 |
| --- | --- | --- |
| [对话进度约定](../skills/task-router/references/progress-display.md) | Agent 在中间消息中维护状态，不是宿主观测的执行轨迹 | 保持不变；不能当成机器可读实时事件源 |
| [Codex 兼容清单](../.codex-plugin/plugin.json) | 注册现有 Hook，没有自定义侧栏配置 | 不假定插件清单可以插入任意 UI |
| [Hook 配置](../hooks/hooks.json) | 生命周期及工具前后事件，命令超时 3 秒 | 新服务不进入 Hook 同步链路 |
| [日志写入器](../scripts/workflow_logger.py#L202-L234) | 哈希技术 ID、工具名称、有限 outcome；无命令和输出 | 能显示活动，不能显示具体命令和测试断言 |
| [Stop 处理](../scripts/workflow_logger.py#L334-L350) | 在 Stop 时解析旧路由行和最终状态行 | 旧元数据不是实时阶段流 |
| [结构化工作流声明](../scripts/workflow_logger.py#L28-L47) | 路由选择/变化、验证摘要、交接和运行结束 | 不包含工作项开始、阶段进度和审批等待 |
| [声明校验与写入](../scripts/workflow_logger.py#L363-L423) | 严格字段集合；补充 source、timestamp、schema_version | 不能向现有接口偷偷塞 session_id 或新事件 |
| [路由变化约定](../skills/task-router/references/route-adjustments.md#L27-L37) | 已启用采集时才使用既有声明接口；不可用时允许缺失 | 有协议不代表每次运行都会有完整事件 |
| [分析器](../scripts/analyze_workflow_logs.py#L80-L174) | 检测声明重放、序列空洞、冲突及结束后事件 | 新看板必须维持至少相同的真实性约束 |

### 3.2 最重要的关联限制

现有 Hook 事件在宿主提供时含哈希后的 `session_id`、`turn_id`、`tool_use_id`、`agent_id`。

结构化声明含 `task_run_id` 和 `event_id`，**不含 session_id/turn_id**。当前严格校验也不允许补入。

因此必须分开建模：

- **会话活动流**：以日志来源和哈希会话/轮次 ID 分组。
- **工作流声明流**：以日志来源和 task_run_id 分组。
- **用户绑定关系**：用户可在旁路中手动指定关联，只表示观察范围，不是宿主证明。

禁止按“时间最接近”“只有一个活动会话”“来自同一目录”自动合并。即使用户绑定，也不能把会话内全部工具活动归为某个任务，或据此计算该任务耗时。

### 3.3 第一版可以显示什么

| 信息 | 可用程度 | 展示规则 |
| --- | --- | --- |
| 工具开始/结束及有限 outcome | 有事件时可用 | 名称、接收时间、配对状态；不显示命令 |
| 工具耗时 | 有配对 duration_ms 时可用 | 显示“已记录执行耗时”；未结束只显示“距开始记录时长” |
| 子 Agent 开始/停止 | 宿主有事件和 ID 时可用 | 生命周期列表；不伪造父子树、负责工作或成果 |
| 路由、风险、规划 Skill | 有声明时可用 | 标注 Agent 声明；Skill 仅为计划使用 |
| 验证、审查、提交、推送结果 | 有摘要时可用 | 独立结果项；不伪装成过程阶段 |
| 当前阶段、剩余工作项 | 现有日志不可用 | 默认不显示，解释“当前数据源未提供” |
| 等待用户、等待审批 | 现有日志不可用 | 不推断；增强适配器有明确事件才显示 |
| 具体测试名称和通过数 | 现有日志不可用 | 不从 outcome 反推 |
| 人类可读任务标题、项目路径 | 现有日志不可用 | 默认生成短别名；允许用户自定义本地别名 |
| Skill 实际加载历史 | 无可靠来源 | 不提供这一指标 |

## 4. Codex 能力验证与路线门禁

### 4.1 调研结论的证据等级

公开源码已确认：

- [`update_plan` 处理器](https://github.com/openai/codex/blob/ddd1812a51f4aded35c3ec5446672474d5cb546b/codex-rs/core/src/tools/handlers/plan.rs)会发送 PlanUpdate；该版本在 Plan 模式下拒绝调用这一 Todo 工具。
- [`update_plan` 工具定义](https://github.com/openai/codex/blob/ddd1812a51f4aded35c3ec5446672474d5cb546b/codex-rs/core/src/tools/handlers/plan_spec.rs)包含 pending/in_progress/completed 三种状态，要求至多一个 in_progress。
- [app-server 的 MCP App UI 描述](https://github.com/openai/codex/blob/ddd1812a51f4aded35c3ec5446672474d5cb546b/codex-rs/app-server/README.md#mcp-app-ui)包含 UI 资源及 inline/fullscreen 偏好相关字段。

这些只能证明源码中存在相应机制，**不能证明**用户安装的桌面版本支持自定义第三方内嵌视图、长期刷新、无侵入订阅或旁路附着现有桌面会话。官方开发文档本次有访问失败，因此不依据未获取内容作能力承诺。

### 4.2 P0 验证清单

在隔离测试环境执行，不修改当前用户 Codex 配置。记录 Codex 产品/版本/平台、插件版本、权限和信任状态、测试步骤、证据及结论。

| 编号 | 验证 | 通过条件 | 未通过处理 |
| --- | --- | --- | --- |
| C1 | 现有插件 Hook 是否被实际加载且用户已信任 | 用户确认的真实普通任务产生同一会话/轮次的工具前后事件、工具名、稳定配对 ID、matched_start/duration/outcome，并观察到 Stop 或 Interrupt | 记录字段级能力矩阵；缺配对等核心能力不通过当前 MVP 门禁 |
| C2 | Codex 自然产生的原生计划如何显示 | 可看到同一计划更新，并记录正常/计划模式差异 | 保持插件原有文字反馈 |

P0 时间盒建议为 1–2 人日。本方案日志 MVP 的硬门禁是 **C1 通过**，不能仅凭会话开始或文件 mtime 通过。若 C1 不通过，只能提供离线原型；若仅 C3 通过，应另建 native-plan-only 变体并重估架构和验收，不沿用当前 P1–P3。C3/C4 不通过不阻塞 C1 已通过的日志 MVP。

C1/C2 是真实目标环境检查；C3/C4 的接口与内嵌探针只在隔离配置中进行，不修改用户当前配置。需要临时 MCP、测试资源或信任调整时先另获授权；否则记未验证。P0 不是要求先实现 P4 的完整集成。

### 4.3 原生计划适配的严格边界

- 不为看板增加每阶段 `update_plan` 调用，不改变 Skill 文本或默认执行步骤。
- 不向原生计划写入失败/阻塞伪状态；其状态集合与业务状态不同。
- 不在计划模式中强制调用该工具，是否可用以目标版本验证为准。
- 只展示真实读取到的计划快照，标注“Agent 计划”，不把 completed 当验收通过。
- 没有稳定 step ID 时，保存各版本快照；不得靠标题相似度自动合并任务历史。
- 新启一个 app-server 不等于附着当前桌面会话；不以此冒充 C3 已通过。

## 5. 产品信息架构

### 5.1 页面结构

一级入口分成“会话活动”“工作流声明”“数据源与诊断”，而非默认一个已自动关联的任务总览。

- 会话活动：来源、短别名、最近事件、活动状态、数据完整性。
- 工作流声明：task_run_id 短别名、已声明路线、验证摘要、结束状态、序列质量。
- 详情页：当前可观测活动、关键失败、事件时间线、来源说明。
- 可选关联区：用户选择绑定的工作流；明确标注“用户绑定，非系统验证”。
- 能力诊断：哪些数据可用、哪些不可用、最后读取成功时间、解析错误计数。

### 5.2 只读 MVP 线框

```text
RelayForge Progress                   本地只读 · 数据源可读

[会话活动] [工作流声明] [数据源与诊断]

会话 A7D2 · 用户别名：权限改造
最近事件：工具开始记录 · 12 秒前
数据状态：可读 / 本轮记录可能不完整

当前可观测活动
shell · 已记录开始，尚未收到结束事件
距开始记录 12 秒 · 不代表进程仍然存活

最近异常
14:35 shell 返回失败
尚无可证明该问题已解决的结果

活动时间线
14:39 工具开始记录
14:38 工具返回成功
14:35 工具返回失败

关联工作流（可选）
未绑定                         [选择已有声明流]

业务阶段 / 测试用例明细
当前数据源未提供，不推断
```

MVP 不默认画“需求→设计→实现→测试→交付”轨道。它会给 Quick、仅规划、仅交接任务增加不存在的阶段。

### 5.3 有真实计划源后的增强视图

在独立区块展示实际计划步骤、当前进行项和历史快照；与工具活动、验证摘要并列。

如果同一计划快照包含 5 项，其中 3 项 completed，可显示“计划项完成 3/5”，不得标成“整个任务完成 60%”。计划改变时保留版本记录，不假定分母稳定。

### 5.4 交互与视觉规则

- 主视图使用文字状态加符号，不只靠红绿颜色。
- 工具事件默认分组/折叠展示，不删除原始事件或把多次动作合并为一次；展开才查看全部元数据。
- 失败记录保留。没有相同检查身份的成功复测，就不能自动标为“已修复”。
- 停止、失败、跳过、未知、不可用必须不同；缺失字段不是 skipped。
- 不持续播放暗示执行活跃的动画；只允许数据连接状态使用轻量反馈。
- 支持中文、亮暗主题、键盘导航、可见焦点、减少动态效果。
- 1280px 桌面下主信息一屏可见；窄窗口纵向排列，事件列表分页或窗口化。
- 页面支持筛选、折叠、别名、用户绑定和本地导出；这些只修改 Companion 自有状态。

## 6. 系统架构

```text
现有 Codex / RelayForge（保持不变）
  └─ 已授权、已工作的既有 Hook/logger
       └─ 元数据 JSONL（只读）
                    ↓
Progress Companion：目录白名单 → 增量读取 → 校验/规范化
                    ↓
               确定性状态投影
                    ↓
       Companion 自有 SQLite（缓存、游标、别名、绑定）
                    ↓
          同源只读 API + 增量事件传输
                    ↓
             本地浏览器看板
                    ↑
   可选：正式只读计划源 / 经验证的 MCP 内嵌壳
```

### 6.1 技术选型

第一版建议 Python 3.11+ 标准库后端 + SQLite + 原生 HTML/CSS/JavaScript。

理由：与现有 Python 日志环境贴近；无需 Node 构建链、第三方运行时依赖、数据库服务或云端账户。界面模块规模控制在本地诊断工具级别，不必先引入前端框架。

- 后端：标准库 HTTP 服务，仅 loopback；有界线程/连接数和超时。
- 状态：纯函数 reducer + SQLite 事务。
- 页面：静态资源自托管，系统字体，不加载 CDN。
- 更新：fetch 流读取 SSE 格式事件；不支持或断流时回退定时快照请求。
- 打包：独立 Companion 包，独立版本；不加入插件清单或插件自动启动链。
- 以后若 UI 规模扩大，再评估前端框架，不作为首版依赖。

上述均为未来实现选择；本次没有创建服务、安装依赖或增加运行时组件。

### 6.2 模块边界

| 模块 | 职责 | 明确不做 |
| --- | --- | --- |
| source registry | 接受本机用户显式配置的日志目录，分配 source_id | 不递归扫描用户主目录 |
| tailer | 按文件代际和字节偏移增量读取 | 不获取 logger 锁、不改源文件 |
| validators | 版本、类型、大小、字段白名单校验 | 不执行记录内容、不做语义猜测 |
| normalizer | 转成 Companion 内部事件 | 不回写既有协议 |
| projector | 构建会话、轮次、工具、工作流声明状态 | 不把 Stop 当任务完成 |
| store | 原子保存游标、规范化事件、投影和用户偏好 | 不保存原始载荷或敏感正文 |
| API/stream | 分页快照与增量更新 | 不提供 shell、Git 或审批 API |
| UI | 展示状态、完整性和来源 | 不调度 Agent |

## 7. 内部数据契约

### 7.1 规范化事件

内部协议独立命名为 `companion_event_schema=1`，不能与 logger 的 schema_version 混用。

```json
{
  "companion_event_schema": 1,
  "ingest_id": 1042,
  "source_id": "src-local-01",
  "source_kind": "hook_metadata",
  "source_position": {
    "file_generation": "gen-02",
    "byte_offset": 8192
  },
  "recorded_at": "2026-11-06T09:00:00.000Z",
  "ingested_at": "2026-11-06T09:00:01.000Z",
  "event_kind": "tool_started",
  "session_ref": "sha256:example",
  "turn_ref": "sha256:example-turn",
  "tool_ref": "sha256:example-tool",
  "task_run_ref": null,
  "provenance": "host_observed",
  "payload": {
    "tool_name": "shell"
  }
}
```

这是内部示例，不是可发送给现有 logger 的输入。真实技术 ID 必须符合其已记录格式。

- source_kind：hook_metadata / workflow_declaration / native_plan（后者默认关闭）。
- provenance：host_observed / agent_declared；用户绑定单独存储，不能改写事件来源。
- recorded_at 为原日志时间，不能声称是精确业务动作发生时间；缺失或无效时置空并记录质量问题。
- ingest_id 为本地数据库单调序号，用于传输游标，不代表业务因果顺序。
- payload 按事件类型白名单保存，未知字段不持久化；禁止通用 raw_payload 字段。
- 会话事件与声明事件的缺失关联字段保留 null，不人工补全。

### 7.2 实体与唯一性

| 实体 | 主键/范围 | 说明 |
| --- | --- | --- |
| source | source_id | 用户配置的单一日志源，避免不同安装数据混淆 |
| session | source_id + session_id | 没有 ID 的事件放隔离区，不按时间补入 |
| turn | source_id + session_id + turn_id | 缺轮次 ID 时仅展示会话级事件 |
| tool_call | source_id + session_id + turn_id + tool_use_id | 不使用工具名称配对 |
| declaration_run | source_id + task_run_id | 与 session 独立 |
| declaration_event | source_id + event_id | 业务字段相同是重放，不同是冲突 |
| user_binding | binding_id + 两侧引用 | 记录用户创建时间和来源，不改变事实事件 |
| plan_snapshot | adapter_id + stable_thread_ref + revision | 仅适配器实测提供稳定关联时启用 |

同一 tool key 出现互相矛盾的多个开始/结束时标记冲突，不静默用最后一条覆盖。没有 key 时允许展示孤立事件，不计算配对耗时。

### 7.3 状态轴必须独立

避免用一个 status 混合所有概念：

- 连接：connected / disconnected。
- 来源读取：readable / missing / denied / unsupported / degraded。
- 事件新鲜度：recent / quiet；安静不代表挂起或离线。
- 会话：open_observed / end_observed / unknown。
- 轮次：start_observed / stop_observed / interrupt_observed / unknown。
- 工具：start_observed / completion_succeeded / completion_failed / completion_unspecified / incomplete / conflicted。
- 声明流质量：intact_open / intact_ended / partial / conflicted。
- 声明结果：保留现有 implementation、minimal_checks 等原始枚举，缺失为 unknown。
- 业务阶段、阻塞原因、等待对象：首版 unknown，不从其他轴推导。

`completion_unspecified` 表示 logger 的 outcome=completed，并不代表成功。`workflow_completed` 表示该声明运行结束，development_status=blocked 时仍然是受阻结束，不是成功。

### 7.4 状态投影规则

1. `session_started` / `session_ended` 仅影响会话生命周期。
2. `turn_started` / `turn_stopped` / `turn_interrupted` 仅影响相应轮次；Stop 不证明整个用户任务已完成。
3. 工具开始只记“已观察到开始”；缺结束不能判断进程仍存活。
4. 工具结束优先展示 logger 已记录 outcome 和 duration_ms；孤立结束不虚构开始时间。
5. `routing_decision` / `workflow_status` 展示在所属会话/轮次，明确是 Stop 时提取的 Agent 声明。
6. `route_selected` 等结构化事件在 declaration_run 内按 sequence 校验并投影。
7. 结构化事件保留 event_id 重放、序列空洞、冲突、路由不连续、缺初始事件及结束后事件检查；结果与现有分析器固定测试样本对齐。
8. partial/conflicted 历史可以显示有效事件详情，但不展示确定性的“最终路线”。
9. 后续成功的任意 shell 不消除先前失败；摘要“检查通过”可以与此前工具失败并存，来源与范围各自注明。
10. 既有摘要没有代码版本指纹或有效范围时，不能把旧通过状态沿用到下一轮修改，显示“历史声明，当前有效性未验证”。
11. 缺字段、未知事件、乱序和时钟回拨降级为诊断，不通过补值形成看起来完整的流程。

## 8. 增量读取、重放与存储

### 8.1 文件读取

- 仅监视用户显式选择目录中的 `events-YYYY-MM-DD.jsonl`，不跟随越界符号链接。
- 源日志以只读方式打开；Companion 缓存在独立用户数据目录，不放进插件日志目录或目标项目。
- 默认 1 秒检查新增字节；没有事件时只做元数据检查，不全量反复读取。
- 首次导入限制在最近 7 天、总读取 100 MiB；超额提示用户选择范围，不能静默截断为完整历史。
- 每条原始记录上限 64 KiB；超限丢弃内容并记诊断计数。该上限是读取防护，不修改 logger 的 16 KiB 声明接口。
- 尾部未换行记录暂存为有界 buffer，等待补全，不立即计作损坏；来源消失后记 partial_tail。
- 检测跨 UTC 日期新增文件、替换、截断和删除。inode/file ID 可用时使用，其他平台使用文件指纹与偏移校验；不能只记文件名。
- 字节偏移必须基于原始字节，不使用 Unicode 字符数。
- 损坏完整行跳过并累计诊断，不把整段原文写进错误日志。

### 8.2 幂等与事务

- 原始记录位置使用 source_id + file_generation + byte_offset 去重。
- 声明事件额外按 event_id 和规范化业务字段去重，接收时间不参与业务等价判断。
- 一次事务提交规范化事件、投影变更和源游标；崩溃后允许重读，不能漏过已前移但未落库的事件。
- 不用“内容哈希相同”删除全部 Hook 重复记录：两个合法动作可能内容相同；无法证明重复时保留并标注异常。
- 原日志被清理后，不宣称可从当前文件恢复已消失历史；缓存重建显示 coverage_start/coverage_end 和缺口。
- 默认缓存保留不超过 7 天且受 100 MiB 上限约束；规范化事件、派生投影、索引和 SSE 日志一致回收，同时维护 coverage 和 SSE 可重放范围。回收截掉声明前序时必须标 retention-limited/partial，不能仍显示 intact。
- 保留期以本地首次 ingested_at 为上限，并对有效的过去 recorded_at 取更早到期时间；无效或未来时间不延长保留期，重新读取保留同一文件代际/偏移的首次接收时间。已超过保留期的历史只可临时导入分析，不默认持久化。
- 若保留历史检查点，标明“截至 revision 的历史快照，当前无法重放验证”，不得据此声称完整历史；容量上限含数据库、WAL 和自有日志预算，需压缩与轮转。
- 别名与绑定可以独立保留，来源对象过期后标注引用失效；用户可删除 Companion 自有数据，不触碰源日志。

## 9. 本地 API 与更新协议

以下为未来接口规格，不表示已有服务。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | /api/v1/health | 最小健康信息，不暴露路径、会话或配置 |
| GET | /api/v1/capabilities | 已验证适配器能力和缺失原因 |
| GET | /api/v1/sources | 来源状态与数据覆盖范围 |
| GET | /api/v1/sessions | 分页会话索引 |
| GET | /api/v1/sessions/{id} | 会话/轮次/工具状态快照 |
| GET | /api/v1/runs | 独立的工作流声明索引 |
| GET | /api/v1/runs/{id} | 声明历史、质量和摘要 |
| GET | /api/v1/events | 按会话或声明流筛选并分页 |
| GET | /api/v1/stream?after={cursor} | 有鉴权的 fetch 流，传输 SSE 格式增量 |
| PATCH | /api/v1/preferences/{id} | 仅修改本地别名和展示偏好 |
| POST/DELETE | /api/v1/bindings | 仅创建/删除用户关联关系 |

数据源新增和目录变更通过本机启动配置完成，不提供任意远程路径读取 API。不存在执行命令、任意文件读取、审批、Agent 控制或 Git 写入接口。

快照返回 `snapshot_revision` 和已包含的 ingest_id。客户端随后订阅 after=该游标，避免快照与订阅之间丢事件。

- 每条增量含 stream id、对象引用及新 revision；客户端忽略已应用 revision。
- 每 15 秒发送连接心跳；心跳只证明 Companion 可达，不证明 Codex 活跃。
- 重连带已应用游标；游标早于缓存范围或数据库 epoch 变化时发送 resync_required，重新获取快照。
- 单客户端队列有界；慢客户端被断开并重同步，不能拖住文件读取。
- 首版最多 5 个浏览器连接；后台页降低渲染频率，不停止必要的数据完整性处理。
- SSE 格式由 fetch 流解析，以便在请求头携带鉴权，不依赖无法添加自定义请求头的原生 EventSource。

## 10. 启动、安装与隔离

### 10.1 用户流程

1. 用户单独下载/安装 Companion，不改变已安装插件。
2. 用户指定插件实际数据根或其 logs 目录；启动器验证并显示只读范围。
3. doctor 检查目录、格式、最近事件和权限。发现历史日志不等于确认当前会话采集成功。
4. 对已有且已信任 Hook 的用户，用一次正常任务确认实时写入。
5. 用户手动启动 Companion；启动器打开本地浏览器，或显示可点击地址。
6. 用户选择会话或声明流，按需命名、绑定、筛选。
7. 用户停止 Companion 后 Codex 与插件继续工作，不受影响。

若 Hook 未启用，只展示现状和既有信任说明；不自动替用户启用或修改配置。

### 10.2 拟议命令

```text
relayforge-progress doctor --log-dir <explicit-existing-log-directory>
relayforge-progress serve --log-dir <explicit-existing-log-directory> --open
relayforge-progress status
relayforge-progress stop
```

这些命令仅描述未来入口，本次没有安装。serve 绑定 127.0.0.1 的系统分配端口；端口冲突不抢占他人进程。stop 只能停止由 Companion 自己记录并验证身份的实例，不能按名称批量杀进程。

首次不创建系统服务；需要自启动时另行提案和授权。停止、崩溃、升级和卸载都不能更改源日志、插件清单、信任设置或业务项目。

### 10.3 部署范围

- 首批实时验收：用户实际使用的 Codex 桌面版本及操作系统。
- macOS/Windows 的文件替换、权限、路径和启动流程分别测试后才列为支持。
- Linux/CLI 单独记录能力矩阵，不能从桌面结果推断。
- 云端任务和远程机器目录不在首版范围；禁止为支持它们把服务绑定到 0.0.0.0。

## 11. 安全与隐私

1. 只绑定 loopback，校验 Host，拒绝非预期 Origin；不启用跨源通配 CORS，防 DNS rebinding。
2. 由启动器产生短期本地能力令牌，不使用 OpenAI API Key，不读取 Codex 登录凭据。
3. 令牌通过 URL fragment 首次交给页面，页面读入内存后清除 fragment；不放 query、不记访问日志、不写 localStorage。刷新后重新从启动器打开属于可接受首版行为。
4. API/流请求通过 Authorization 头鉴权；所有修改本地偏好的请求还须同源校验和 JSON Content-Type。
5. 启动器和实例控制文件仅当前用户可读；令牌随进程结束失效。受限目录之外不持久化令牌。
6. 静态资源同源，配置 CSP、frame-ancestors 'none'、nosniff、Referrer-Policy: no-referrer、敏感响应 no-store；默认不允许 iframe 嵌入。
7. 工具名、模型名等字符串也视为不可信：限制长度、使用 textContent、禁止 HTML/Markdown 注入、禁止生成可执行链接。
8. 只把白名单元数据送到浏览器；真实源路径仅在必要的本机配置步骤显示，不进入普通诊断导出。
9. 用户别名可能含业务信息，默认仅本地保存，不进入诊断包。
10. 错误日志只记录错误码、来源内部 ID 和计数，不输出原始行、命令、正文或任意环境变量。
11. 不同浏览器页共享本机用户的已授权来源，不提供多用户隔离承诺；同机恶意进程及已被控制的浏览器不在此令牌机制的防护承诺内。
12. 诊断导出为显式操作，导出前预览字段；默认不包含别名、路径、原始技术 ID 或原始日志。
13. 日志中的哈希 ID 是稳定假名，不是匿名化保证；不同导出可能被关联，时间、模型和工具信息也可能敏感。
14. 本地日志没有签名，拥有源目录写权限的进程可能伪造内容。host_observed 标签只表示按已知 Hook 格式归类，不是密码学证明；界面说明“本地记录，未经签名验证”，不将其用于审计或授权。
15. 历史导入与实时新增明确区分；重放旧事件不能触发新任务、失败弹窗或系统通知。首版不启用系统通知。

本地能力令牌是 Companion 访问防护，不是外部账户凭据。若未来引入 MCP 或第三方依赖，必须单独评审、授权、锁定版本；本方案不自动批准安装。

## 12. 可选增强：Codex 内展示

### 12.1 原生计划只读适配器

只有 C3 通过才实现：

- 输入为正式接口提供的真实计划更新和稳定 thread 标识。
- 输出为独立 plan_snapshot；允许在适配器内部将已验证的原始会话 ID用与 logger 一致的算法映射，但不能猜测不同 ID 体系是否等价。
- 严格字段过滤，不保存说明正文或工具输入输出。计划步骤文本可能含业务信息，默认关闭持久化，并单独告知用户。
- 不调用 thread/start、turn/start、resume 或其他可能接管任务的接口来实现只读浏览。
- 断开时保留最后快照并标过期；不回退到抓取 Codex 私有存储或屏幕识别。

如果获得计划必须扩大隐私范围或依赖会话写操作，C3 判为不满足本方案，不能为了好看的阶段轨道放宽边界。

### 12.2 MCP App UI 内嵌适配器

这不是首版必需项，且本次不新增 MCP。C4 通过、用户后续明确授权后，才另建独立 Companion 集成：

- 只提供显式打开状态视图的只读工具/资源，不加入现有插件清单，不注册自动运行 Hook。
- 初次打开由用户操作；需要一次显式工具调用或模型请求时单独征得授权，后台刷新不再次请求模型。若用户要求严格零额外模型请求，则必须有宿主直接打开资源的正式机制，否则不采用该路线。
- 使用宿主确认支持的资源协议、CSP、消息通道及隔离方式，不能直接把浏览器鉴权 URL 塞进 iframe。
- 访问 scope 由本机用户在 Companion 中单独授权，默认仅一个会话或一个声明流，可撤销；它不是第 3.2 节的观察关联。模型不能扩大 scope，工具参数不接收目录、任意 source 或文件路径，读取/刷新/重连均校验同一 scope。
- 能否长期刷新、历史卡片是否静态、休眠恢复和重连均须实测；每次刷新需要模型调用则不采用此路线。
- 不承担审批或任务控制，不把第三方 UI 的存在当作插件已运行的证据。
- 不支持时返回浏览器入口或明确不可用，不注入 Codex 客户端、不修改安装包。

### 12.3 后续业务阶段事件

本项目不修改既有声明 schema、不新增阶段汇报工具、不在 Skill 中插入上报步骤。

若未来仍要求完整、可靠的业务阶段进度，而原生计划源不可读，必须另立“可选生产侧进度协议”项目并重新授权；不能将其混入本次只读实现。这是能力边界，不是待实现时随意补齐的细节。

- T03：定义内部事件、状态轴、接口和错误码；准备正反例 fixture。
- T04：实现白名单目录、字节游标、半行/轮转/截断和事务恢复。
- T05：实现会话活动、独立声明流及质量诊断投影。
- T06：实现本地服务、鉴权、快照、增量、重连和限流。
- T07：实现索引、详情、诊断、用户绑定和无数据状态。
- T08：完成安全、真实性、性能、平台测试及既有回归。
- T09：独立打包、启动/停止/卸载说明和实际用户试用。
- T10：仅在门禁通过后另排可选增强，不把它隐含在首版完成条件里。

## 15. 验收标准

### 15.1 真实性和产品验收

| 场景 | 期望结果 |
| --- | --- |
| 一次正常工具调用 | 开始、结束、配对耗时清楚；不自动标“实现完成” |
| 工具 outcome=completed | 显示“已结束，未提供成功结论” |
| 工具失败后任意其他工具成功 | 原失败仍保留，不自动变成已解决 |
| 后续摘要检查 passed | 显示“Agent 声明通过”，不宣称修复了某次无身份的失败 |
| 没有新事件 5 分钟 | 显示上次更新时间和安静状态，不声称在思考、卡死或等审批 |
| Stop 到达 | 结束该轮次的观测状态，不自动结束整个工作流 |
| workflow_completed + blocked | 显示“运行已结束，结果受阻”，不是绿色成功 |
| 只有日志历史，没有当前采集证据 | 显示历史可读、实时采集未验证 |
| 两个会话和两个 task_run 交错 | 默认完全分离，不按时间关联 |
| 用户手动绑定 | 显示用户绑定标识，不归因任务耗时或成功率 |
| 声明重放、空洞、冲突 | 幂等或明确 partial/conflicted，最终路线不伪造 |
| 缺少阶段数据 | 无阶段轨道，解释来源缺失，不放虚拟默认流程 |
| commit/push=skipped | 保留“声明未执行/跳过”，不显示为未完成必做任务 |
| 用户仅规划或仅交接 | 不自动添加实现、测试、推送的待办阶段 |
| 旧检查结果与新一轮改动 | 标历史声明，当前有效性未验证 |

### 15.2 工程与安全测试

- 读取：UTF-8 跨块、CRLF、半行、超大行、坏 JSON、重复键、未知 schema、错误类型、文件轮转/截断/删除、时钟回拨。
- 恢复：事务前后注入崩溃，重启无漏读；缓存丢失可重建并标覆盖缺口；SSE 游标过期触发重同步。
- 隔离：只读打开源目录；不申请 logger 锁；读权限拒绝、SQLite 写失败、服务崩溃都不影响 Codex。
- 安全：外部 Origin、非法 Host、无/错令牌、跨源修改请求、路径穿越、符号链接越界、恶意字符串 XSS、慢连接和队列溢出。
- 隐私：fixture 中放入 prompt、command、output、secret 等未知字段，确认不进入数据库、API、页面及诊断导出。
- 兼容：结构化声明测试与现有分析器固定结果对齐，不通过修改既有测试来迁就 Companion。
- 不变性：运行前后受保护资产摘要、Git 状态以及项目写入范围一致；源日志只允许原 logger 的正常追加，不能由 Companion 修改。
- 回归：实施阶段执行现有 `python3 -m unittest discover -s tests -v`，新增 Companion 测试单独执行；本次文档交付不宣称这些运行时测试已执行。

### 15.3 性能预算

以下为待实测目标，不是已取得结果：

- 正常 1 秒轮询下，完整记录落盘到前台页面更新 P95 ≤ 2 秒。
- 基准：10 个会话、100,000 条事件、5 个页面连接；正常流 20 条/秒，突发 100 条/秒持续 60 秒。
- 基准机记录 CPU、内存、磁盘和 OS；冷启动索引 100,000 条事件目标 ≤ 10 秒，期间 UI 显示导入中。
- 无新数据时 CPU 平均 < 单核 1%，服务 RSS 目标 < 150 MiB；若未达标，先收缩缓存和连接上限，不通过丢事件达标。
- 网络流每连接队列上限 1,000 条或 1 MiB，先到为准；溢出断流重同步。
- 不给既有 Hook 新增任何同步步骤、网络请求和模型调用。看板引起的磁盘竞争通过对照测试记录，不能仅以“旁路”宣称零性能影响。

### 15.4 用户价值门禁

不能仅以“页面能打开”宣布成功。试用者应能在 10 秒内区分：有新活动、某工具失败、只是无新事件、运行声明已结束但受阻、缺少阶段数据这五种情况。

若试用反馈仍然只是“更漂亮的工具调用列表”，应停止扩展图表，优先评估 C3 的真实计划读取能力；没有数据源时明确产品上限，而不是增加虚假的阶段状态。

## 16. 风险、降级与回滚

| 风险 | 处理 |
| --- | --- |
| 用户期待完整业务进度，源数据不足 | 首屏解释能力；真实计划源不通过时不宣传业务阶段可视化 |
| Hook 不加载或未被信任 | 诊断未验证，提供既有说明；不自动修改信任 |
| 声明事件很少或不完整 | 独立显示，保留 partial；不补事件 |
| Codex 内嵌能力变化 | 独立版本适配器；默认浏览器入口不受影响 |
| 原日志无项目名/任务标题 | 本地别名；不读取源代码和提示词猜名称 |
| 长命令缺结束 | 记录“未见结束事件”；不无限显示已验证的运行中 |
| 隐私泄露 | 字段白名单、局部令牌、同源、禁正文、导出预览 |
| 观察服务异常影响工作 | 无生产侧调用依赖；停 Companion 即恢复原体验 |
| 缓存损坏或过期 | 丢弃 Companion 缓存并从仍存在的源日志重建，标覆盖缺口 |
| 功能范围膨胀为调度平台 | 所有执行、审批和发布能力明确禁止 |

回滚：停止 Companion → 移除单独安装包与其自有数据（用户选择）→ 若另装过可选适配器则单独撤销该集成。既有插件、源日志和业务项目不应需要任何恢复操作。

## 17. 完成定义与后续决策

首版完成必须同时满足：

- 在目标 Codex 环境通过 C1，确认既有 Hook 实时日志和核心配对字段可用；仅原生计划源可用时另立变体。
- 会话活动和工作流声明分离，用户关联有来源标签。
- 无数据、失败、中断、未知、部分历史可清晰区分。
- 服务不修改插件和工作流，也不额外请求模型。
- 安全/隐私/性能/回滚测试有可复现报告。
- 独立安装、启动、诊断、停止和卸载流程可用。
- 不依赖未验证的 Codex 侧栏、内嵌 UI 或既有会话附着能力。

默认后续决策：

1. 优先启动 P0，不直接建设复杂 Dashboard。
2. P0 成功后交付浏览器只读 MVP；原生计划能读取时增量接入。
3. MCP App UI 仅作为独立可选集成，需要实测和额外授权。
4. 不能得到业务阶段数据时保留事实边界；任何生产侧进度协议改动都重新立项。

**最终定位：这是一套不干预插件运行的观察与解释界面，不是重新设计插件工作流，也不是控制 Agent 的第二个调度器。**
